# Known limitations and verification status (v0.4.0a1 Alpha / Project Atlas Development)

This document transparently identifies architectural boundaries, risk areas, and verification status for Parquet Guard.

- **Release Status & Package Distribution:** `v0.4.0a1` is released on GitHub Releases. Public distribution on PyPI and TestPyPI has been verified through GitHub OIDC Trusted Publishing workflows. The current work on branch `feat/project-atlas-real-world-interoperability` (PR #6) is unmerged developmental engineering under review; no release tag (e.g. `v0.5.0a1`) has been pushed.
- **Hosted CI & Test Matrix:** Cross-platform continuous integration is executed across Ubuntu, macOS, and Windows spanning Python 3.9 through 3.13 via GitHub Actions. Test passes in CI prove test suite execution within the specific matrix jobs, not permanent defect-free guarantees in arbitrary production environments.
- **Zero-Data-Scan vs. Runtime Engine Probes:** "Zero Data Scan" strictly describes metadata-only inspection (`inspect_schema`, static `audit_dataset`, and static contract comparison), which reads exclusively Parquet metadata footers. Runtime query engine verification (`verify-engine`, `verify_engine_compatibility`) and migration sandbox sampling operate on row samples up to `--row-limit` and require appropriate data access authorization.
- **Parquet Footer Checksums vs. Full-File Tamper Proofing:** `compute_footer_checksum` parses the 4-byte uint32 `footer_len` from the Parquet trailer and cryptographically hashes the entire `FileMetaData` Thrift structure. This detects any modification to schemas, column descriptors, row-group metadata, statistics, and key-value properties with $O(1)$ I/O. It does not hash unreferenced binary payload pages and should not be construed as full-file tamper-proofing.
- **StorageBackend Cloud Lakehouse Boundaries:** The `StorageBackend` abstraction (`LocalStorageBackend`, `MemoryStorageBackend`, `RemoteStorageBackend`) provides an experimental foundation using `fsspec` for slice reads and metadata stats. The main CLI (`parquet-guard audit`) is designed for local directories; remote S3/GCS URLs are experimental and not yet end-to-end integrated into all CLI workflows.
- **Engine Runtime Probes as Specific Evidence:** Runtime compatibility probes on DuckDB, Polars, and PyArrow represent empirical observations on specific engine versions, operations (READ, CAST, SCHEMA_UNION), and bounded row samples. They are empirical evidence, not permanent guarantees against all possible edge-case rows in production.
- **DuckDB & Polars CAST Strictness:** Strict `CAST` operations are verified to prevent silent conversions. DuckDB `TRY_CAST` null injection checks ensure non-null data is not masked as NULLs. Unmappable data types return `UNSUPPORTED`, preventing vacuous passes.
- **MCP Server Transport & Sandboxing:** The Model Context Protocol server operates over standard I/O (stdio), enforces JSON-RPC 2.0 error framing, bounds JSON payload sizes and synthetic `sample_rows`, refuses to overwrite existing HTML reports unless `overwrite=True`, and sandboxes file access strictly within `--allowed-dir`. Row-level execution probes enforce strict default-deny (`user_data_authorized=False` default); only literal boolean `True` within permitted directories authorizes row probes. Omitted, non-boolean, or unauthorized calls fail closed with zero data rows read.
- **Unified Engine Probe Authorization & Bounded Limits:** Both Python API (`verify_engine_compatibility(..., allow_row_probe=False)`) and CLI (`parquet-guard verify-engine --allow-row-probe`) enforce explicit opt-in for row data access. Sampling row limits are strictly validated positive integers ($1 \le \text{row\_limit} \le 10,000$); non-integers, booleans, and values $\le 0$ are rejected before any data decoding occurs.
- **Multi-Engine Aggregation & Fail-Closed Gates:** Explicitly empty requested engines (`engines=[]`) or operations (`operations=[]`) return `NOT_RUN` and fail overall compatibility. When multiple engines or operations are requested, any missing, unsupported, or inconclusive component marks the overall verification as non-passing (`overall_compatible=False`), ensuring partial executions cannot masquerade as full passes.
- **Consumer Contracts 2.0 Criticality & Evolution Direction:** Technical compatibility (`COMPATIBLE`, `CONDITIONALLY_COMPATIBLE`, `INCOMPATIBLE`) is strictly separated from CI policy (`is_blocking`). `INFORMATIONAL` consumers report accurate technical incompatibility but never block CI pipelines (`is_blocking=False`, `blocking_fields=[]`). `STANDARD` consumers block CI only on critical requirement violations, while `CRITICAL` consumers block on any violation. Full directional evolution is computed via `evaluate_consumer_evolution()`: `BACKWARD` tests if the new consumer can read baseline data, `FORWARD` tests if the old consumer can read target data, and `FULL` requires both directions to hold simultaneously. Field renames are properly reconciled in extra-field and column-ordering policies.

See `tests/` and submit reproducible bug reports through GitHub Issues. Before declaring a stable release, fix or explicitly constrain the affected capabilities and run a real platform test matrix.
